## 目标与范围

将 AgentWork 的版本固定、共享前端、分平台后端及原生客户端构建、兼容校验和部署固化为同一套工具；将 WikiMan 从实验包迁入正式产品范围；补充开发职责规范；将离线知识库编辑和同一块实时协同纳入后续版本需求。

服务端兼容 Linux 和 macOS。Mac 和 iOS 使用本地打包前端，Web 和移动浏览器加载服务端前端，各端共用所选后端。当前移动原生目标是 iOS；Android 原生工程不在本计划范围内。继续采用单个可信所有者跨设备使用，不建设企业多用户权限体系；现有服务认证、TLS、编辑器授权和写入校验继续保留。

## 当前基线

WikiMan 位于 `packages/experimental/wikiman/`，包名为 `@deepseek-ai/dsh-wikiman`；改造后的内核和编辑器源码位于 `native/wikiman/wiki-kernel/` 与 `native/wikiman/wiki-app/`。DSH 工作台与 WikiMan 原生编辑器共同提供知识库能力。

现有入口包括 `native/wikiman/build.sh`、`scripts/prepare-agentwork-server.ts`、`apps/desktop/scripts/prepare-remote-frontend.ts`、`apps/desktop/scripts/electron-builder-remote.config.mjs` 和 `apps/ios/scripts/`。目前已有单端构建与资源指纹校验，但没有贯穿所有平台的统一发布流程。

现有 portable 同步通过快照和摘要识别冲突、保留冲突副本；它不提供块级实时协同。断线时保留界面或输入不等于知识库支持离线编辑。已有文档与页面写入校验不能直接删去，改成无条件覆盖。

现有运行与构建说明见[服务端部署](../../../docs/cookbook/deploying-agentwork-server.zh.md)、[iOS 客户端](../../../apps/ios/README.zh.md)和 [WikiMan runtime](../../../native/wikiman/README.zh.md)。这些文档描述现状；本计划描述增量。历史验收结果不能代替新发布的验收证据。

## R1：构建与发布

### 发布流程

固定源码与依赖 → 构建一次共享前端资源包 → 分平台构建后端 → 组装 Mac/iOS 客户端 → 校验兼容性和运行行为 → 汇集不可覆盖的发布目录 → 显式部署或分发。

统一入口放在 `scripts/agentwork/`，提供 `build`、`verify`、`release`、`deploy --dry-run`、`deploy` 和 `rollback` 等操作；参数、报告和当前支持范围见命令参考、[人工手册](../../../docs/cookbook/releasing-agentwork.zh.md)与 [Agent 技能](../../skills/agentwork-release/SKILL.md)。CI 调用同一实现，不复制一套发布逻辑。共享资源按 WikiMan 包名发现源码，构建接口不依赖实验目录名称；正式迁包与构建工具可独立验收。

### 版本与产物

发布清单至少记录发布标识、源码提交、工作区状态、依赖锁文件摘要、构建工具版本、平台与架构、接口版本、知识库格式版本、产物摘要及校验结果。开发构建可允许脏工作区，但不得作为正式发布产物；正式发布拒绝未提交修改。产物不包含访问令牌、模型密钥、签名私钥或用户知识库。

共享资源范围包括 DSH Web、所有被打包的客户端插件及其分块、CSS、字体、语言、图片、Wiki 编辑器资源和许可证声明。服务端和原生客户端使用同一份资源；同一提交号不能替代字节一致性校验。需要实现服务端资源导入与加载流程，不能将原生客户端的资源目录直接当作服务端部署目录。

Linux 和 macOS 分别编译目标平台的原生依赖与 Wiki 后端。Mac/iOS 在 macOS 构建；签名和设备授权使用平台已有机制。不能把源码目录的链接、其他平台的 `node_modules` 或开发机绝对路径带入服务端运行包。服务端仍通过 `dsh` profile 启动。

### 兼容与发布控制

校验应覆盖清单格式、全部声明资源的缺失及篡改、平台架构、协议与知识库格式兼容性，以及客户端/服务端资源配套。失败时不激活新版本。需要用真实运行组合验证知识库编辑保存、Agent 读取已提交新版和引用原文，区分模型回放与真实模型调用的证据。

程序版本目录与 `home`、`library`、`workspace` 数据目录分离。部署支持只读预演，显式指定目标与版本；执行前检查活动 Agent 任务、编辑器保存状态及数据备份，确认安全后切换程序并做健康检查。不得通过强杀编辑器或覆盖数据目录完成升级。

程序回退与数据回退分别设计。发生数据格式升级时，只允许经验证的兼容回退或备份恢复；不得承诺任意降级。中断、健康检查失败、磁盘不足和未知提交结果都需要明确报告及恢复步骤。

### 人工与 Agent 入口

人工手册提供准备环境、构建、验收、部署、回退和签名步骤。Agent 技能说明同一脚本的参数、结构化结果、退出状态、重试条件、平台授权交接和任务记录要求。构建或检查成功不等于获准更新运行中的服务或分发应用。

## R1：GitHub Actions 构建、发布与部署

GitHub Actions 承接版本构建与发布，其实际运行、签名和部署环境验证状态登记在 TODO，不以 YAML 文件存在代替验收。Actions 调用 `scripts/agentwork/` 的统一脚本，人工本地执行与 Agent 执行使用相同参数和校验；YAML 只负责事件、任务依赖、runner、凭据和产物传递。

### 仓库与触发方式

先审计现有 `.github/workflows/`。继承的 DSH 配置包含专用 runner、上游分支约定、COS 发布和组织变量，不能直接作为 AgentWork 发布能力使用。保留源码来源与许可证，按实际用途隔离、停用或适配这些工作流；不要因历史文件存在就声明 CI 已就绪。

使用独立命名的 `agentwork-ci.yml`、`agentwork-build.yml`、`agentwork-release.yml` 和 `agentwork-deploy.yml`。PR 和 `develop` 更新运行必要检查，`develop` 推送及手动操作构建配套产物，手动发布选择精确成功 run/attempt。仓库默认分支为 `develop`，产品标签使用 `agentwork-v<根清单版本>`；同版本不同源码或不同资产拒绝覆盖。继承的上游任务在 AgentWork 仓库中隔离。

### 任务依赖与产物传递

固定提交与工具链 → 检查源码 → 单次构建共享前端并上传工作流产物 → Linux/macOS 后端与 Mac/iOS 客户端下载同一份资源并构建 → 汇集摘要并执行兼容及运行验收 → 按明确操作生成 GitHub Release → 单独触发部署。

资源传递使用不可混用的发布标识、提交号和摘要。依赖缓存只用于加速安装，不能替代发布产物或跳过兼容检查；签名私钥、令牌和用户数据不得进入缓存或工作流产物。工作流产物保留期与正式 Release 资产用途分别定义，重试必须验证取到的仍是同一次发布的资源。

runner 的操作系统、架构、Node/Go/pnpm/Xcode 版本需要显式配置并记录。优先使用满足目标要求的 GitHub 托管 runner；必要的自托管 runner 单独登记。Linux/macOS 原生后端分别构建，不能让矩阵任务各自重新生成共享前端。所有声明交付的目标都通过验收后，才允许整套发布标记成功。

### Apple 签名与 iOS 安装范围

iOS 默认 CI 检查可先提供模拟器构建；可安装真机包和发行包必须分别验证签名、描述文件、设备或分发方式。当前普通 Apple 账号本地直装流程保留，个人描述文件续期和设备授权需要人工处理，不承诺无人值守生成长期可分发包。缺签名配置应报告该目标未交付，不能将未签名或模拟器产物标成可安装 IPA。

Mac 开发构建、Developer ID 签名和公证分开标识。签名作业使用受限凭据、临时钥匙串和退出清理；缺证书或公证配置不应静默降级后发布为正式签名版本。配置签名时再通过 GitHub Secrets 或受控 runner 提供凭据，不将凭据写入源码。

### 发布和私网部署

GitHub Release 只发布已校验的程序包、清单、摘要、许可证和说明；发布动作与普通 PR 检查分离，不默认开启上游 COS 或其他分发目的地。创建草稿、正式发布、重复执行及失败重试的语义需要固定，禁止覆盖同版本下内容不同的资产。

部署采用独立的手动入口和显式目标环境，先提供预演，再按环境策略执行版本切换、健康检查和回退。现有开发机在公司内网/VPN，GitHub 托管 runner 不应被假设能够直接连接其私网地址；需确认受控自托管部署 runner 或获准的连接方式。预演和构建不得隐式更改运行服务。

凭据按作业授予最小权限：普通检查只读，Release 作业才获得发布所需写权限，部署凭据限目标环境。部署使用已校验的 SSH 主机身份；来自不可信 PR 的代码不能获得签名、部署秘密或在可信内网部署 runner 上执行。环境保护应适合当前单个所有者的操作方式，不引入企业账号系统。

### 验收与使用说明

人工可从 Actions 界面选择输入、查看结果和下载产物；Agent 可通过已授权的 GitHub CLI/API 触发相同工作流、跟踪 run 和 attempt、读取结构化报告。手册与技能需说明缺工具、无权限、作业排队、取消、部分矩阵失败、产物过期及部署未知结果的处理，不能仅以某个 job 绿色判断整套发布成功。

失败验收至少覆盖：错误提交或版本、缺失/篡改共享资源、混入其他构建的产物、缺签名、未通过兼容校验、私网不可达、重复发布和部署健康检查失败。既验证拒绝不合格发布，也验证可在隔离环境完成构建、Release 和部署恢复。

实现依据见 [GitHub 工作流产物](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)和[部署环境](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)。实施时重新核对当前功能可用性、runner 配额和签名要求，不沿用本计划作为平台能力保证。

## R1：正式产品包与开发职责

拟迁移到 `packages/knowledge/wikiman/`，保留 npm 包名。同步修改路径别名、编译项目、测试、产品分类、依赖安装、资源路径、许可证检查及双语文档。正式归属必须有明确的 AgentWork 产品组合和真实组合验收，不应通过删除实验分类登记绕过产品可达性检查。

优先保留完整 WikiMan 插件，在包内划分职责；只有独立消费者或演进周期需要时才进一步拆包。普通 DSH 默认组合不因本次迁移自动启用知识库；AgentWork 的组合名称和配置入口需在实施时确定。已有 profile 的旧链接安装路径需要迁移指引，不能只移动源码。

| 能力 | 归属 |
| --- | --- |
| 通用 Agent 工具与外部系统连接 | 对应独立 DSH 插件 |
| 知识库业务、检索、导入、同步、协同编排 | `packages/knowledge/` |
| 原生文档读写及原子提交 | `native/wikiman/wiki-kernel/` |
| 富文本、块交互及协同编辑器适配 | `native/wikiman/wiki-app/` |
| 工作台导航、页面、设置及连接反馈 | 对应 `packages/client/` 插件 |
| 原生网络、钥匙串、相机、分享等系统能力 | `apps/desktop/` 或 `apps/ios/` |
| 构建、产物清单、兼容检查和部署编排 | `scripts/agentwork/` |

开发规范还应明确配置所有权、错误处理、生命周期、国际化、数据迁移、测试证据，以及哪些变更要求重打客户端。规范沿用根目录和子目录 AGENTS，不另建互相冲突的规则。

## R2：离线编辑需求

支持用户明确缓存的文档在离线时打开和编辑。缓存以服务端身份、store ID、文档 ID 和数据格式版本隔离，不能仅以 URL 或标题区分。首次从未缓存的文档应明确显示不可离线打开；未缓存附件不得显示成已下载。

本地持久化包含已确认基线、待提交操作及其唯一标识、必要附件和同步状态。界面区分本地已保存、待同步、服务端已提交和冲突。进程重启可恢复已持久化输入，重复传输不产生重复修改；认证失效、磁盘不足或写入失败不能伪报已保存。

重连时先校验服务端、库身份和格式，取得确认结果后清理待提交记录。R2 若尚不支持自动合并同块并发修改，必须保留双方可恢复版本，阻止静默覆盖。切换服务端、清除缓存、旧库导入和 portable 同步与待提交编辑之间的关系必须明确。

服务端 Agent 只能读取已同步并确认提交的内容。离线待同步内容应向用户明确标注，不能声称其他设备或服务端 Agent 已经可见。离线运行 Agent 不在本计划范围内。

## R3：实时协同需求与选型

候选方案为 Yjs 或 Automerge，优先验证 Yjs。选型尚未定稿；不能因为有通用富文本绑定就假设现有 Wiki 编辑器可以直接接入。技术参考：[Yjs 离线持久化](https://docs.yjs.dev/getting-started/allowing-offline-editing)、[Yjs 增量更新](https://docs.yjs.dev/api/document-updates)、[Automerge 富文本](https://automerge.org/docs/reference/documents/rich-text/)。

原型需验证稳定块 ID、富文本标记、有序子块、块移动与删除、中文输入法、每端撤销、离线重放和重复/乱序消息。现有未知字段、大整数标识、附件和文档导出应保持可恢复；不得把整篇文档转成一个覆盖式字符串来冒充同块协同。

服务端需持久化协同更新、确认进度和检查点，再通过受控事务生成内核可读取的已提交文档。明确协同记录与文档投影的权威来源、崩溃恢复、压缩和垃圾回收规则，避免两份可独立写入的数据互相覆盖。

编辑器、Agent 写入、导入、恢复和 portable 同步都需遵循统一写入规则。对启用协同的文档，拒绝绕过协同版本检查的旧写入路径。迁移需要格式标记、版本兼容检查、可验证备份和中断恢复，生产启用前完成持久化变更记录与升级指南。

Agent 读取和引用绑定已提交版本及内容摘要。引用点击后若文档已变化，应标明变化，不能把新内容当成旧引用原文。验收覆盖同一所有者的 Mac、iOS 和 Web 并发编辑；不将其扩展为企业账号体系。

## Agent 续接规则

先读本文件和 TODO，再检查真实分支、工作区及相关 AGENTS；当前工作区可能包含尚未提交的已有功能，禁止重置或覆盖。按 TODO 依赖选择未完成事项，实施前确认尚未定稿的接口或数据模型，更新对应的当前状态文档。

TODO 是任务状态的唯一登记处，PLAN 是目标、范围和验收原则的依据。完成任务须记录文件、实际运行的检查和结果；只有存在有效验收证据才勾选。未测平台、签名或设备阻塞需显式登记。每轮结束留下下一步和阻塞原因，不将原型通过、构建通过或历史结果写成正式交付完成。
